## IA verdicts (hypothesis vs. code evidence)

### (a) Is "Growth" the right label for inquiries/partners/pipeline?
**Verdict: mostly yes, but the current implementation splits the concept across three unlabeled surfaces, undermining the name.** The catalog already has a `growth` link (`/app/growth`) *and* a separate top-level `demand-inbox` link labeled "Demand" (`/app/inquiries`, aliased from `/app/admin/inquiries`), *and* `partners` living in an unrelated "Network" group with `regions`/`locations`. `/app/growth/page.tsx` pulls `getGrowthCommandCenter`, `getFlywheelSnapshot`, `getWeeklyOperatingSummary`, `getManagementBriefing` — i.e. it already is the pipeline/flywheel/campaign command center a human would call "Growth." But a staff member scanning the current nav sees "Demand," "Growth," and "Partners" (under "Network") as three separate things, with no visible link between them. The human mental model — "who's interested in us, and how do we turn that into revenue" — is one job (Growth), but the code exposes it as three disconnected nav entries. Recommendation: keep "Growth" as the top-level label, fold Demand/Inquiries in as its default view (attention-triage), and move Partners out of "Network" into Growth (partners are pipeline/relationship accounts, not delivery infrastructure like regions/locations).

### (b) Do staff think "Programs," not "Delivery"?
**Verdict: yes — the code agrees. Kill the "Delivery" group label.** `lib/operations.ts`'s `ProgramDetail` (line 867) treats Class as the child concept of Program at every level: readiness checks are phrased entirely in terms of "Class exists," "Class is missing an eligible lead," "Class has no active lead-instructor," "Class is below minimum enrollment," "Class is missing an upcoming first session" (`lib/operations.ts:517-623`). There is no independent "Delivery" object in the data model — delivery *is* Program → Class → Session. Yet `lib/navigation/catalog.ts` currently renders a nav group literally named "Delivery" containing Classes and Curriculum, separate from the top-level "Programs" link. This creates two doors to the same operating concept: a user has to guess whether "what's going on with the Track 201 cohort in Denver" lives under Programs or Delivery. Recommendation: collapse Delivery into Programs — Classes and Curriculum become contextual/filtered views reached from a program record or from Programs' own sub-navigation, not a sibling top-level group.

### (c) Does Work (`/app/tasks`) merit top-level nav?
**Verdict: keep it, but as the aggregate/audit view only, not a primary destination.** `/app/tasks/page.tsx` already implements the plan's target shape — it renders `mine/overdue/upcoming/delegated/waiting`-style groupings (weekly commitment cycle, review/submit controls, governance controls) sourced live from Postgres (`getDb`, `lib/people-operations`). It is the one canonical task model the plan requires (no parallel systems). However, cross-entity task frequency in the current code shows tasks are *already* meant to be entity-contextual: `WorkItemActions`, `SubmitWorkControls`, `ReviewSubmissionControls` are generic components reused wherever work happens (teach page, hiring, tasks). Keeping `/app/tasks` as a single top-level nav item is right (it is the only place to see "my/overdue/delegated" across every entity at once) — the risk is staff defaulting to it as a to-do list disconnected from the record it's about. No demotion needed; the fix is contextual surfacing elsewhere (Stage 7), not removing the nav item.

### (d) How should Admin be tucked away?
**Verdict: current placement (separate collapsed group, `admin`-role only) is structurally correct but the codebase has a second, undeclared admin surface that must be reconciled first.** `lib/navigation/catalog.ts`'s `platform-admin` group is already visually and permission-wise separated from BOW HQ links (roles: `["admin"]` only, growth never sees it) — this matches the plan's "must not compete visually with operating work." But there is an entirely separate, non-catalog admin dashboard at the **top-level** route `app/admin/page.tsx` (outside `app/app/`), using its own data layer (`lib/admin.ts`'s `getAdminData`) and its own component (`components/admin/AdminDashboard`), unreachable from any nav link inspected. This is a duplicate admin surface, likely a pre-cutover leftover from before the current `/app/admin/*` group existed. It must be found via direct URL only (`/admin`), which is itself a bad admin-discoverability story and a stray parallel system the plan's hard rules would flag ("no parallel systems"). Recommendation: fold or delete `/admin` before finalizing the Admin group's disposition (see route matrix).

## Cross-cutting friction patterns found in code

- **Two parallel data layers on the same routes**: 11 files still call `useAppState` (`grep -rn "useAppState" app/`): `app/app/admin/{page,cohorts,invitations,organizations,people}.tsx`, `app/app/instructor/{page,cohort}.tsx`, `app/app/settings/page.tsx`, and the three Legacy student components. Every one of these is a CRUD-shaped screen driven by an in-memory snapshot rather than Postgres — exactly the "database with a frontend" problem named first in the plan's priority list.
- **A second, un-navigated admin dashboard**: `app/admin/page.tsx` (top-level, outside `app/app/`) uses its own `lib/admin.ts`/`getAdminData`/`AdminDashboard` stack, unreachable from any nav catalog entry found in this audit. This is a stray parallel system per the plan's hard rules and needs an explicit disposition, not silent abandonment.
- **Redirect stubs already exist and work as designed**: `/app/admin/inquiries` → `/app/inquiries`, `/app/instructor/session` → `/app/classes` or `/app/teach/classes` by role. These validate the plan's "retire early, delete late" pattern and should be the template for other legacy consolidations.
- **DB terminology leaking to users**: nav labels "Cohorts," "Organizations," "Invitations," "LMS Cohorts" expose table/record names directly instead of the job a human is doing (e.g. "LMS Cohorts" should read as a legacy-migration concern, not a permanent admin concept).
- **Group labeling actively contradicts the data model**: "Delivery" (Classes + Curriculum) as a nav group separate from "Programs," while `lib/operations.ts` models Class strictly as a Program child — see IA verdict (b).
